## 6. Система доступа через QR-коды

### Иерархия прав:

```
Суперадмин (ты)
  └─ Генерирует QR для админа здания
       └─ Админ здания
            ├─ Генерирует QR передачи прав → новый админ, старый теряет
            └─ Генерирует QR регистрации жителя → житель вводит имя/пол
                 └─ Житель
                      ├─ Смотрит расписание
                      └─ Отмечает отсутствие/болезнь
```

### Схема БД:

```sql
CREATE TABLE building_tokens (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    building_id INTEGER NOT NULL REFERENCES buildings(id),
    token TEXT NOT NULL UNIQUE,
    role TEXT NOT NULL CHECK(role IN ('admin', 'resident')),
    used_by_name TEXT,          -- заполняется когда кто-то отсканировал
    used_by_gender TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    used_at TEXT,
    active INTEGER NOT NULL DEFAULT 1
);

CREATE INDEX idx_building_tokens_token ON building_tokens(token);
CREATE INDEX idx_building_tokens_building ON building_tokens(building_id);
```

### Логика токенов:

| Кто | Что генерирует | Роль токена | Эффект |
|-----|---------------|-------------|--------|
| Суперадмин (ты) | QR для здания | `admin` | Сканер становится админом здания |
| Админ здания | QR передачи прав | `admin` | Новый сканер = админ, старый деактивируется |
| Админ здания | QR регистрации | `resident` | Сканер вводит имя/пол → становится жителем |

### Токен живёт пока:
- Не использован (`used_at IS NULL`)
- Деактивирован вручную

## 8. Навигация (menu.js)

Отдельный скрипт `static/menu.js`, подключается на каждой странице. Как в Gratis/Arethusa — IIFE, инжектирует навигацию + CSS.

### Паттерн:

```js
// static/menu.js — IIFE
(function() {
    const token = localStorage.getItem('ds_token');
    let user = null;

    // При загрузке — проверяем токен через /api/auth/me
    async function init() {
        if (!token) { showActivateLink(); return; }
        try {
            user = await fetch('/api/auth/me?token=' + token).then(r => r.json());
        } catch(e) {
            localStorage.removeItem('ds_token');
            showActivateLink();
            return;
        }
        renderNav();
    }

    function renderNav() {
        // Админ: расписание + управление + QR-коды
        // Житель: расписание + мои отсутствия
        // Без токена: кнопка "Активировать"
    }

    // Экспорт для страниц
    window.ds = { token, user, api };

    init();
})();
```

### Страницы:

| URL | Роль | Что показывает |
|-----|------|---------------|
| `/` | admin | Полная админка (периоды, люди, комнаты, заполнение) |
| `/view` | resident | Просмотр расписания + свои отсутствия |
| `/activate?token=XXX` | any | Активация токена (регистрация) |

### Навигация в меню:

**Админ:**
- 📋 Расписание (главная)
- 👥 Люди
- 🏠 Помещения
- 🔀 Периоды
- 📱 QR-коды (передать права / зарегистрировать жителя)

**Житель:**
- 📋 Расписание
- 🏥 Мои отсутствия

**Без токена:**
- 🔗 Активировать токен

### Хранение сессии (localStorage):

- В localStorage сохраняется **только токен** (`token`)
- `building_id`, `role`, `name` — **всё определяет сервер** по токену
- Каждый API-запрос содержит токен (query param `?token=XXX`)
- Если токена нет → редирект на `/activate`
- Если токен деактивирован/использован → очистить localStorage, показать ошибку

```json
// localStorage:
{"token": "abc123"}

// Ответ сервера при проверке токена:
{"building_id": 1, "building_name": "Лоджия 4", "role": "admin", "name": "Борис"}
```

### API:

```
POST   /api/tokens              — создать токен {building_id, role}
GET    /api/tokens?building_id=X — список токенов здания
DELETE /api/tokens/:id           — деактивировать токен

GET    /api/activate?token=XXX   — проверить токен, вернуть info
POST   /api/activate             — активировать токен {token, name?, gender?}
GET    /api/auth/me              — текущий пользователь по токену (из заголовка/params)
```

### Сценарии:

**1. Суперадмин назначает админа здания:**
- Суперадмин жмёт «Создать QR для админа» возле здания
- Генерируется ссылка: `https://domain.com/activate?token=abc123`
- Суперадмин показывает/пересылает QR
- Человек сканирует → попадает на страницу активации
- Если роль `admin` и нет данных пользователя — сразу активирует
- Запись в `building_tokens`: `used_by_name`, `used_at` заполнены

**2. Админ здания передаёт права:**
- Админ генерирует новый QR с ролью `admin`
- Предыдущий админ деактивируется (его токен → `active=0`)
- Новый сканер активируется

**3. Админ регистрирует жителя:**
- Админ генерирует QR с ролью `resident`
- Сканер попадает на страницу → вводит имя, выбирает пол
- Человек добавляется в `people` здания, токен активируется

### Фронтенд:

**Страница `/activate?token=XXX`:**
- Загружает токен, показывает: здание, роль
- Если роль `admin` → «Вы стали админом [Лоджия 4]»
- Если роль `resident` → форма: имя, пол → кнопка «Зарегистрироваться»
- После активации → сохраняем токен в localStorage, редирект на `/`

**Все страницы:**
- При загрузке → читаем токен из localStorage
- Если нет токена → редirconт на `/activate`
- Все API-запросы → токен в заголовке или query param
- Сервер проверяет токен и определяет building_id/role/name

**Админка `/` (суперадмин):**
- В панели здания — кнопка «QR-код для админа»
- Список активных токенов

**Админка (админ здания):**
- Кнопка «Передать права» → генерирует QR admin
- Кнопка «Зарегистрировать жителя» → генерирует QR resident
- Список токенов + история

**Житель (`/view?token=XXX`):**
- Просмотр расписания
- Кнопка «Отметить отсутствие» (своё имя, даты, причина)

## 7. Публичная страница просмотра (обновление)

**URL:** `/view` (с токеном в localStorage)

### Что показывает:
- Расписание дежурств текущего здания
- Таблица: кто где дежурит в какие дни
- Рейтинг
- Отсутствующие помечены

### Житель может:
- Смотреть расписание
- Отмечать своё отсутствие/болезнь (с — до, причина)
- Видеть свою позицию в очереди

### НЕ может:
- Назначать/удалять дежурства
- Заполнять периоды
- Редактировать людей/помещения

## 8. Серверная защита API по ролям

### Middleware `require_role`:

Каждый API-эндпоинт помечается required role:

```rust
// Пример: вызов в хендлере
let ctx = db.validate_token(&token)?;  // возвращает {building_id, role, name}
require_role(&ctx, "admin")?;          // если роль не подходит → 403
```

### Реализация:

```rust
struct AuthContext {
    building_id: i64,
    role: String,      // "admin" или "resident"
    name: String,
}

fn require_role(ctx: &AuthContext, required: &str) -> Result<(), StatusCode> {
    if ctx.role != required && ctx.role != "superadmin" {
        Err(StatusCode::FORBIDDEN)
    } else {
        Ok(())
    }
}
```

### Суперадмин:
- Единственный суперадмин — определяется в конфиге или первом здании
- Может создавать/удалять здания
- Может генерировать QR для админов зданий
- В плане пока не выделяем отдельно — можно добавить позже
